# /jobflow:fit

`/jobflow:intake` 와 `/jobflow:apply` 사이에 들어가는 단계다. intake 의 자격요건 검사는 "지원 가능한가"만 보지만, fit 은 "어느 자리에 지원해야 하는가"를 정한다.

## 왜 필요한가

대기업 공고는 한 번에 수십 개 직무를 연다. JD 를 끝까지 읽어 보면 내 전공이 열려 있는 직무가 몇 개뿐인 경우가 흔하다. 노션에 "IT / 영업·마케팅 등"처럼 뭉뚱그려 적힌 채로 지원서를 다 채운 뒤 직무를 잘못 골랐음을 알면 전부 낭비다. 그래서 지원서를 채우기 전에 직무를 정한다.

## 시작 점검

1. `${user_config.workspace_dir}/config.yaml` 이 있는지 본다. 없으면 `/jobflow:setup` 을 먼저 돌리라고 안내하고 멈춘다
2. 프로필을 읽는다: `${user_config.workspace_dir}/profile/master.yaml` 과 `profile/experiences/` 의 경험 카드. 없으면 `/jobflow:setup` 이나 `/jobflow:experience` 를 안내하고 멈춘다. 프로필은 이 컴퓨터 밖으로 보내지 않는다
3. 노션 커넥터를 확인한다(`${CLAUDE_PLUGIN_ROOT}/reference/connectors.md`). 대상 행은 config `notion.jobs_ds` 에서 찾는다
4. 안전 원칙은 `${CLAUDE_PLUGIN_ROOT}/reference/safety.md` 를 따른다

## 규칙

1. JD 원문 문구를 그대로 인용한다. 요약해서 "데이터 역량 요구"라고 쓰지 말고 `"SQL, Python 등을 통해 데이터를 분석해본 경험"` 처럼 옮긴다. 자소서가 이 문구를 되받아야 한다
2. 없는 경험을 만들지 않는다. 매칭이 약하면 약하다고 쓴다
3. 탈락 판정에도 근거를 남긴다. 나중에 같은 회사에 다시 지원할 때 재사용된다
4. 자격 판정(경력, 학위, 졸업 연도, 어학 등)은 `${CLAUDE_PLUGIN_ROOT}/reference/intake-gate.md` 를 따른다. 직무명이나 태그를 근거로 삼지 않는다

## 절차

### 1. JD 확보

- 공고에 첨부된 PDF 가 1순위다. 로그인 없이 받을 수 있는 경우가 많다
- PDF 는 Read 도구로 직접 본다(`pages` 로 나눠 읽는다. 한 번에 20쪽까지). `pdftotext` 가 설치되어 있으면 텍스트 추출에 써도 된다. 없어도 동작한다. 이미지 기반 PDF 는 `pdftotext` 가 빈 파일을 뱉으니 Read 로 시각적으로 읽는다
- JD 와 별개로 "지원서 입력 가이드" 류 문서가 있으면 반드시 같이 읽는다. 학력 입력 범위 같은 항목이 숨어 있어, 차단 사유로 봤던 gap 이 사실은 선택 항목이었던 일이 있다

### 2. 전공 게이트로 1차 필터

국내 대기업 JD 는 직무마다 `자격요건` 또는 `Who we're looking for` 첫 줄이 사실상 전공 게이트다. 여기서 대부분 걸러지므로 먼저 이걸로 후보를 좁힌다. 내 전공은 profile 의 학력 항목과 config `eligibility.majors` 에서 읽는다.

| 판정 | 기준 |
|---|---|
| ✅ 통과 | 내 전공이 명시적으로 나열됨 |
| △ 조건부 | 인접 전공으로 걸칠 수 있으나 불확실 (예: 내 연계전공 <전공 A> 와 JD 의 '컴퓨터 계열') |
| ❌ 탈락 | 전혀 다른 계열 |

### 3. 통과한 직무만 요구사항 한 줄씩 대조

표로 만든다. 왼쪽은 JD 원문, 오른쪽은 마스터 프로필과 경험 카드의 구체적 자산이다.

```markdown
| JD 요구 문구 | 대응하는 내 자산 |
|---|---|
| "재무제표에 대한 지식과 데이터 기반 분석" | <인턴십 이름>: 재무 데이터 분석 업무 |
| "중국어 활용이 가능한 분" | <외국어> 일상회화 (profile 의 어학 항목) |
| "반도체 기초 공학 이해" | ⚠️ 공백: 보완 필요 |
```

### 4. 순위와 근거

1지망, 2지망을 정하고 왜 그 순서인지를 3가지 이내로 쓴다. 좋은 근거는 다음과 같다.

- 희소성: 그 조건을 만족하는 지원자가 드문가 (예: 두 외국어를 동시에 보유)
- 교집합: 두 영역을 한 사람이 덮는가 (예: 재무제표 이해 + 데이터 분석)
- 통과 확률: 요구 수준이 낮아 오히려 붙기 쉬운 자리인가
- 근무지와 전형 부담: 코딩테스트 여부, 근무지가 현실적인가

약점은 반드시 함께 쓰고 상쇄 방법을 붙인다. 약점 없는 매칭 보고서는 신뢰할 수 없다.

### 5. 지망 슬롯 확인

지원서에 1지망, 2지망 필드가 있으면(예: 지망 직무 필드) 두 개를 다르게 쓴다. 1지망은 적합도 최고, 2지망은 통과 확률이 높은 안전판이다.

### 6. 노션 기입

대상 행의 본문 맨 아래에 `## JD 분석 (YYYY-MM-DD)` 섹션으로 넣는다. 구성은 다음과 같다.

```
1. 전공 게이트로 N개 직무를 거른 결과   (표. 탈락 사유 포함)
2. 1지망 권고 - <직무명>                (JD 원문 ↔ 내 자산 대조표 + 핵심 논거 3가지 + 약점과 대응)
3. 2지망 권고 - <직무명>
4. 비권장                               (왜 안 쓰는지)
5. 정정 사항                            (이전 판정을 뒤집은 게 있으면)
6. 입력 규칙                            (가이드 문서에서 나온 것)
7. 자소서/경험기술서 소재               (문항 원문 + 소재 우선순위. 문장은 쓰지 않는다)
8. 전형 일정
```

공고에 급여가 적혀 있으면 config `filters.salary_floor` 와 비교해 결과 맨 위에 한 줄로 표시한다(예: `급여: 원문 "<급여 문장>" - 기준 이상` 또는 `기준 미달`). 기준이 null 이거나 공고에 급여가 없으면 "급여 미명시"로 둔다. 추측하지 않고, 미달이어도 자동으로 탈락시키지 않는다. 판단은 사용자 몫이다.

속성도 갱신한다. `직무` 를 실제 지망 직무명으로 바꾸고, `비고` 첫 줄에 결론을 적는다. 같은 날 다시 돌리면 기존 섹션을 덮어쓰지 말고 날짜를 달리해 새 섹션으로 붙인다.

## 산출물이 흘러가는 곳

- `/jobflow:apply`: `직무` 속성이 지원 분야 선택의 입력값이 된다
- 자소서 소재 정리: 7번 섹션의 소재 우선순위가 출발점이다
- 면접 준비: 2번 섹션의 약점과 대응이 예상 질문 목록이 된다

## 금지

- JD 를 요약만 하고 원문 문구를 버리는 것
- 프로필에 없는 경험을 대응 자산으로 적는 것
- 자소서 문장을 대신 쓰는 것. 소재 우선순위까지만 정한다
- 프로필 원문을 노션에 붙여 넣는 것. 대응 자산은 경험 이름과 한 줄 요지만 적는다
